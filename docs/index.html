Design and Implementation of an 8-Bit Custom CPU Core with Cache Hierarchy

Author: F.R. Sujeevan (2nd Year Computer Engineering Student)

Department of Computer Engineering, University of Peradeniya

1. Introduction and Learning Objectives

During my second year of undergraduate studies in computer engineering, my primary goal was to bridge the gap between theoretical digital logic concepts and practical hardware design. While textbook diagrams introduce processors through simplified functional blocks, building a complete, working CPU core requires addressing real-world hardware details such as propagation delays, memory latency bottlenecks, gate-level arithmetic, and control signal generation.

The architecture and instruction set of this processor are inspired by the MIPS RISC architecture as presented in the textbook Computer Organization and Design: The Hardware/Software Interface, Sixth Edition, by David A. Patterson and John L. Hennessy. Guided by these principles, I designed and implemented an 8-bit custom central processing unit in Verilog HDL.

While foundational memory primitive modules and utility tools were provided as course starter resources, all core processor architecture logic, instruction decoding, register file operations, ALU functions, 2's complement logic, and cache hierarchy subsystems were designed and implemented independently by me.

2. Instruction Set Architecture Design

Selecting an appropriate Instruction Set Architecture was the first step in my design process. Inspired by MIPS fixed-length instruction encoding, I chose a 32-bit fixed-length instruction format for my 8-bit data path. This decision simplified instruction fetch and decode logic, allowing every instruction to be fetched cleanly without requiring variable-length multi-cycle instruction assemblies.

The 32-bit instruction word is partitioned into four distinct 8-bit fields:

  1. Opcode Field (bits 31 to 24): Specifies the operation to be executed by the processor.
  2. Destination / Immediate Field (bits 23 to 16): Identifies the target destination register (RD) or holds an 8-bit immediate value or branch target offset.
  3. Source Register 1 Field (bits 15 to 8): Specifies the first source operand register (RT).
  4. Source Register 2 / Immediate Field (bits 7 to 0): Specifies the second source operand register (RS) or an 8-bit immediate operand.

3. Low-Level Datapath Engineering

Register File Design

In reg.v, I implemented an 8-by-8-bit register file providing eight general-purpose registers (r0 through r7). The register array features two asynchronous read ports, allowing simultaneous reading of REGOUT1 and REGOUT2 with an artificial propagation delay of 2 time units. Register writes are synchronous and occur on the rising edge of the clock signal when the write enable line is high, subject to a 1 time unit write delay. A master reset signal clears all register contents to zero upon system initialization.

Modular Arithmetic Logic Unit

Rather than relying on a single monolithic block, I structured the ALU in alu.v using individual sub-modules to model hardware propagation delays accurately:

  • Forward Unit: Modeled with a 1 time unit delay to pass immediate or register values directly to output.
  • Add Unit: Modeled with a 2 time unit delay to perform binary addition.
  • AND Unit: Modeled with a 1 time unit delay to perform bitwise logic AND.
  • OR Unit: Modeled with a 1 time unit delay to perform bitwise logic OR.

Subtraction and Zero Flag Generation

To implement subtraction without extra adder hardware, I constructed a 2's complement logic block. The second register operand is inverted and incremented by one (~REGOUT2 + 1) with a propagation delay of 1 time unit. The result is then routed into the addition sub-module.

I also incorporated a Zero Flag circuit that evaluates the output of the ALU. When an ALU computation yields zero, the zero signal is asserted. This signal plays a crucial role in conditional branch evaluation, enabling branch execution when comparing two registers for equality in the beq instruction.

Control Unit and Signal Routing

The central control unit in cpu.v inspects the incoming opcode asynchronously. Upon decoding, it asserts appropriate control signals: setting write enable for register updates, configuring ALU operation select lines, driving immediate selection multiplexers, toggling memory read/write requests, and resolving target branch addresses.

4. Memory and Cache Hierarchy

A critical phase of my design involved modeling realistic memory delays. Main memory access is inherently slower than register operations. In my simulation, main memory accesses require 40 time units per block access. To prevent severe performance degradation, I designed separate instruction and data cache memories.

Instruction Cache Subsystem

The instruction cache module in icache.v is a direct-mapped cache with a capacity of 128 Bytes organized into 8 cache lines, where each line stores a 16-Byte data block (equivalent to 4 32-bit instructions).

The 10-bit instruction address received from the Program Counter is divided into three fields:

  1. Tag Field (bits 9 to 7): 3 bits used to verify cache line ownership.
  2. Index Field (bits 6 to 4): 3 bits used to select one of the 8 cache lines.
  3. Offset Field (bits 3 to 0): 4 bits used to select the specific byte or word within the 16-Byte block.

When an instruction is requested, the cache checks if the line is valid and matches the requested tag. A hit allows instant instruction delivery. On a miss, the cache finite state machine stalls the CPU core by asserting a busywait signal and issues a 16-Byte block read to the main instruction memory, incurring an 81-cycle miss penalty before resuming instruction execution.

Data Cache Subsystem

The data cache module in dcache.v is a 32-Byte direct-mapped cache structured into 8 lines of 4 Bytes each. It operates on a Write-Back policy with Dirty Bit tracking and a Write-Allocate strategy on write misses.

The 8-bit memory address is mapped into Tag (bits 7 to 5), Index (bits 4 to 2), and Offset (bits 1 to 0). On a read or write access:

  • Read Hit: The requested byte is extracted from the cached 4-Byte block and returned in 1 cycle.
  • Write Hit: The target byte within the cache line is modified directly, and the dirty bit for that line is set to indicate uncommitted memory state.
  • Miss with Clean Line: The cache fetches the required 4-Byte block from data memory into the cache line.
  • Miss with Dirty Line: The finite state machine first evicts the dirty block by writing it back to data memory, then reads the required block from memory into the cache line.

5. Pipeline Stall Mechanics

To maintain correctness during memory transactions, I engineered a unified stall signal: 

assign BUSYWAIT = DCACHE_BUSYWAIT || ICACHE_BUSYWAIT;

Whenever either cache experiences a miss, BUSYWAIT goes high. In the CPU control logic, an active stall signal immediately freezes the Program Counter (PC <= PC) and forces the register file write enable to zero. This prevents partial state updates, instruction execution corruption, or invalid memory writes while waiting for cache line fills.

6. Software Toolchain and Module Contributions

To compile and execute programs on my CPU architecture, a software assembly toolchain is used:

  1. Assembler Program (Assembler.c): Authored by Isuru Nawinne for the CO2070 laboratory course, this C program translates assembly source code into 32-bit machine code text files.
  2. Memory Formatting Script (generate_memory_image.sh): Authored by Kisaru Liyanage, this shell script converts 32-bit machine code into Verilog $readmemb memory array input files (instr_mem.mem).

The main instruction memory (instruction_memory.v) and data memory (dmem_for_dcache.v) modules were provided by course instructor Isuru Nawinne as underlying physical storage primitives. All core processor logic—including the top-level CPU datapath (cpu.v), modular ALU (alu.v), register file (reg.v), instruction cache (icache.v), data cache (dcache.v), and simulation testbench (cpu_tb.v)—were authored and designed by me.

7. Verification and Simulation Results

I validated the processor by writing a test assembly program in program.s to calculate the Fibonacci sequence from F(0) to F(8) and store the results (0, 1, 1, 2, 3, 5, 8, 13, 21) into data memory addresses 0x00 through 0x08.

The simulation was executed using Icarus Verilog, and signal timing waveforms were inspected in GTKWave using cpu_tb.v. The waveform output confirmed proper instruction decoding, correct branch evaluation during loop iterations, cache miss stalls during initial line fills, and final write-back storage of calculated Fibonacci numbers in memory.
